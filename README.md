# 遮瑕師類型測驗 — 可部署版

**首頁 ＋ 測驗合在同一個檔案**，點 CTA 直接切換到測驗，不換頁、不閃白。
不需要伺服器、不需要建置、零外部依賴，丟上 GitHub Pages 就能跑。

```
07-可部署測驗/
  index.html        首頁 + 11 題測驗 + 結果頁（單檔）
  income.html       收入路徑試算（單檔，可獨立分享）
  images/           55 張圖（講師、學員得獎、49 張結業照片牆）
  README.md
```

首頁結構：Hero → 這是為你準備的 → 三個問號 → 3分鐘之後你會拿到
→ 數字帶 → 講師 → 學員得獎 → 結業照片牆 → 收尾 CTA
＋ 手機版底部固定 CTA。全頁共 5 個入口都會進到測驗。

照片牆預設只顯示 12 張（桌機剛好 5 列不缺角），按「看更多」才展開其餘 37 張。
橫式合照 (`grad-03/05/06/13/16/19/30/31/35`) 會跨兩欄——這幾張是橫著排開的大合照，
硬裁成直式會把兩側的人切掉。50 張全部 `loading="lazy"`。

## 三分鐘上線

**1. 改設定**

打開 `index.html`，最上面有一段 `window.CONFIG`，只要改這裡：

```js
BOOKING_URL_A : "https://..."   // 沒填過申請表的人 → 導去申請表／預約頁
BOOKING_URL_B : "https://..."   // 填過但沒預約的人 → 導去直接選時段的頁面
WEBHOOK_URL   : ""              // 選填，結果 POST 到這裡給 Setter 看
LIFF_ID       : ""              // 選填，填了會一起送出 LINE userId
```

**2. 上傳 GitHub**

```bash
git init
git add index.html images/ README.md
git commit -m "遮瑕師類型測驗"
git branch -M main
git remote add origin https://github.com/你的帳號/你的repo.git
git push -u origin main
```

**3. 開啟 Pages**

Repo → Settings → Pages → Source 選 `main` / `root` → Save
約一分鐘後網址是 `https://你的帳號.github.io/你的repo/`

## 兩種受眾怎麼分辨

沒有後端，所以用**網址參數**：

| 對象 | 網址 | 結果頁 CTA |
|---|---|---|
| 填過申請表、沒預約 | `.../?applied=1` | 「你上次已經走到最後一步了」＋不用重填 |
| 什麼都沒填 | `.../?applied=0` | 「補完最後幾題，預約顧問時間」 |
| 不確定 | 不帶參數 | 測驗最後會多問一題請他自己回答 |

**LINE 圖文選單可以直接設不同網址**——已預約名單那格掛 `?applied=1`，
新好友歡迎訊息那格掛 `?applied=0`。這樣多數人是零摩擦的。

之後如果接了 LIFF ＋ 後端，可以改成用 userId 自動比對，把這段參數邏輯換掉即可。

## 結果怎麼回到 Setter 手上

`WEBHOOK_URL` 留空時，結果只會印在瀏覽器 console（測試用）。

填了之後會 POST 這包 JSON：

```json
{
  "ts": "2026-08-11T15:30:00.000Z",
  "lineUserId": null,
  "mainType": "客人捨不得換型",
  "subType": "好東西藏不住型",
  "pace": "兼職起步",
  "axisP": 2, "axisE": -4,
  "safety": 3,
  "applied": false,
  "answers": [1,-1,1,-1,1,-1,1,-1,2,1,3]
}
```

最省事的接法是 **Google Apps Script**：發布成網頁應用程式，把回傳寫進試算表，
網址貼進 `WEBHOOK_URL` 就好。Make 或 n8n 的 webhook 也可以。

> 用 `mode:'no-cors'` 送出，所以不會因為跨域失敗擋住使用者，
> 但也讀不到回應。這對「單向記錄」的用途是刻意的取捨。

## 計分邏輯（已通過窮舉測試）

**軸 P（人 ↔ 技）**：Q1、Q3、Q5、Q7，人 +1／技 −1
**軸 E（放大 ↔ 深耕）**：Q2、Q4、Q6、Q8，放大 +1／深耕 −1
Q1、Q2 分別是兩軸平手時的決勝題。

```
P=0 且 E=0                → ⑤ 什麼都想試試型（無副型）
其餘依象限：
  P>0,E<0 → ② 客人捨不得換    P>0,E>0 → ③ 好東西藏不住
  P<0,E<0 → ① 慢工出細活      P<0,E>0 → ④ 越做越想開店

副型 = 翻轉絕對值較小的那一軸；相等時翻 E 軸
       （保證是相鄰象限，絕不會出現對角組合）

節奏 = 動機×2 + 時間×1.5
  ≤5 兼職起步 ／ 5.5–8 轉職探索 ／ >8 創業發展
```

Q11（安全態度）不計分，只進 Setter 情報。

**驗證結果**：窮舉 2,304 種作答組合，15 組課程文案全部可達、
無對角副型、無主副型相同、⑤探索型出現率 14.1%。

## 已知限制

1. **沒有後端**，所以身分辨識靠網址參數，不是真的比對資料庫。
2. **結果不會存在你這邊**，除非設定 `WEBHOOK_URL`。
3. **`?applied=1` 是可以被使用者自己改的**——但這個參數只影響 CTA 文案，
   不涉及權限或金流，被改了也沒有實質風險。
4. 對應表中標為**推論**的 5 組文案（見 v2 對應表的缺口清單），
   建議正式對外前由真人審過。

## 收入路徑試算（`income.html`）

**四個控制項**：可運用時間（1–140 小時／週）、**課程階段每月找得到幾位模特（0–15）**、
開始接客後每月能約到幾位（0–132），以及逐月推演右上角的達成率（100／80／60%）。
預設是「每週 10 小時・普通 6 位・兼職每天 1 位・達成率 80%」。
往下推十二個月，輸出一張平滑折線圖＋一張逐月表。

### 為什麼客源要拆成兩條

課程階段要湊滿 **15 位免費模特**才能開始收費，這跟結業後約付費客人是**兩個完全不同的漏斗**：
前者要找人免費被施作（公司預約系統紀錄顯示，有到場的學員每場平均只做 1.64 位、
112 位學員無人達到 15 位），後者是一般的美業接客。用同一條滑桿代表兩者，
會讓「每天約 1 位客人」這種合理假設連帶把找模特也講得太輕鬆。

每個月的推演順序是：**先扣回購客的時間 → 再補課程階段缺的模特 → 模特補滿之後，
同月剩下的時間才開始接付費客人**。所以跨關那個月的表格會出現「1 位模特＋16 位客人」。

| 找模特按鈕 | 位／月 | 換算依據 |
|---|---|---|
| 懶散 | 3 | 每月跑一場實作課，做滿 3 位（每位 2 小時、6 小時場次上限 3 位） |
| 普通 | 6 | 每月跑兩場，都做滿 |
| 積極 | 12 | 每月跑兩場，另外自己再帶 6 位 |

> ⚠️ 這三個是**規劃用的節奏，不是實測值**。公司預約系統的完整紀錄顯示，
> 有到場的學員每場平均只做 **1.64 位**、112 位學員無人達到 15 位
> （2025-02-27～2026-08-05，245 筆有效施作，涵蓋率 99.3%，平均完成 2.19 位）——
> **連「懶散」的 3 位／月都比實測樂觀**。
>
> 依指示，這段對照**沒有寫在頁面上**；頁面下方的資料出處只說明三個節奏是怎麼換算的。
> 這份 README 保留這筆數據，是為了讓之後改這頁的人知道實測基準在哪裡。

### 接客後的四種情境（以每月 22 個工作天換算）

按下去會**同時設定時間與客源兩條滑桿**——兼職／全職本來就是成套的。
`week` 是「光接新客就需要」的週時數（2 小時 × n ÷ 4.33），回購客的時間再另外擠。

| 按鈕 | 位／月 | 週時數 |
|---|---|---|
| 兼職・每天 1 位 | 22 | 10 |
| 兼職・每天 2 位 | 44 | 20 |
| 全職・每天 4 位 | 88 | 41 |
| 全職加班・每天 6 位 | 132 | 61 |

### 達成率

「人會偷懶、會有意外」，所以達成率**同時打在「排得出的時間」與「兩條客源」上**。
只打人數的話，時間吃緊時回購客會自動把空檔補滿，達成率就完全看不出差別
（實測：40 小時／週 × 88 位，三個達成率都算出同一個數字）。

小數用**累進**不四捨五入：3 位 × 80% = 2.4，`round` 掉會跟「2 位」算出同一個結果，
按鈕看起來就像壞的。改成把小數存著、攢滿一位才多做一位；當月沒用完的額度不遞延（名單會過期）。

以每週 10 小時、接客 22 位、達成率 80% 為例，模特那條的差別：

| 找模特 | 折算後 | 做完 15 位 | 第 12 個月 |
|---|---|---|---|
| 懶散 3 位 | 2.4 | 第 7 個月 | 79,800 |
| 普通 6 位 | 4.8 | 第 4 個月 | 92,000 |
| 積極 12 位 | 9.6 | 第 2 個月 | 96,000 |
| **0 位** | 0 | **永遠不會** | **0** |

### 階段與定價

| 累積服務人數 | 階段 | 新客每位 | 這群人日後回購 |
|---|---|---|---|
| 1–15 | 課程階段 | 免費模特（不計收入） | — |
| 16–45 | 見習遮瑕師 | NT$2,000 | NT$1,800 |
| 46–90 | 正式遮瑕師 | NT$4,000 | NT$3,600 |
| 91 以上 | 資深遮瑕師 | NT$4,000 | NT$3,600 |

**回購價鎖定在「這位客人第一次施作時的階段價」×0.9，不會因為你升階就跟著漲。**
所以回購客分兩群記帳：半價模特那一群永遠 1,800，全價客那一群 3,600；
你跨進正式之後，只有「之後才接的新客」才進 3,600 那一群。回購率兩群都是 80%，
第 2 個月起計，免費模特不進回購池。時間不夠時先排單價高的那一群。

所有假設都在檔案最上面的 `window.ASSUMPTIONS`，要調數字只改那一段。

### 階段進度條的規則

條的末端 = 累積人數在**上方階梯那條軸上的位置**，兩者共用同一把尺。

實作上是直接讀階梯每一格「實際渲染出來的位置」再內插，不是用抽象比例算的——
因為欄寬是 `minmax(118px, Nfr)`，實際比例會隨螢幕寬度變形，只有讀真實幾何才對得齊。
最後一階沒有上限，視覺刻度取 130 位（＝90＋40），超過就一直是滿的。

> 舊寫法是「累積 ÷ **當前階段**的上限」，分母會隨階段跳動，結果是**升階時進度條會倒退**：
> 15→16 位從 100% 掉回 36%，45→46 位從 100% 掉回 51%，90→91 位掉回 76%。已修正。

> 窄螢幕時階梯會折成 2×2 兩排，這時水平位置不再代表進度（第 3 格跑回最左邊，
> 46 位會算成 1%）。所以會先判斷是不是排成一列，折行時改用線性刻度 `累積 ÷ 130`。

### 圖表怎麼畫的

- **單一數列 ＋ 一條參考線，刻意不用雙 Y 軸**。階段進度改用折線圖下方的色帶表示。
- 四階用**同一色相由淺到深的序列色階**（`--s1`～`--s4`），因為階段是有序的、不是並列類別。
  相對亮度 .699→.427→.171→.050 單調遞減，四階的文字對比都過 WCAG AA 小字門檻 4.5（最低 4.67）。
- 平滑用 Catmull-Rom 轉三次貝茲，控制點夾在繪圖區內，避免平滑造成負值溢出。
- 只在第 3／6／12 個月直接標值，不是每點都標。表格同步在月份欄標里程碑色。
- 滑鼠移過去有十字線與浮動說明；手機上圖表自己橫向捲動（`min-width:640px`），
  否則 12px 的字會被壓到 4px 看不見。

> 客源上限從 20 拉到 132 之後，先前「週時數滑桿右半段沒作用」的問題自然解決了：
> 132 位 × 2 小時 = 264 小時／月（約 61 小時／週），加上回購客根本吃不完，
> 整條 1–140 的滑桿從頭到尾都有意義。
